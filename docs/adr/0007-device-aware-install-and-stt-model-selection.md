# ADR 0007: 端末対応インストール導線とSTTモデル自動選択

## 状態

採用

## 背景

ReleaseにはOS・CPU別の成果物があり、利用者がファイル名から適切なものを判断する
必要がある。また、固定の軽量STTモデルは導入しやすい一方、十分なメモリを持つ端末で
利用可能な文字起こし精度を活かせていない。

## 課題

- READMEから新規導入と更新を同じ操作で開始できるようにする。
- 開発リポジトリの情報を公開配布リポジトリへ含めない。
- 低メモリ端末を不安定にせず、高性能端末では高精度モデルを案内する。
- モデル取得前に容量と選定理由を明示し、配布元とchecksumを固定する。

## 選択肢

1. Release一覧を維持し、利用者が成果物を選ぶ。
2. 全OSを含む独自ブートストラップを配布する。
3. 公開静的ページでOS候補を絞り、既存のOS別インストーラとアプリ内モデル選定を使う。

## 採用した案

選択肢3を採用する。公開静的ページはブラウザ内でOS候補を絞り、Releaseの安定名
成果物へ案内する。macOSのCPU種別を確定できない場合はApple SiliconとIntelを
明示して選択可能にする。

アプリはApple Siliconかつ総メモリ8GB以上、またはその他のCPUで16GB以上の場合に
`large-v3-turbo-q5_0`、それ未満で`base-q5_1`を推奨する。モデルは公式配布URL、
正確なサイズとSHA-256が一致した場合だけ保存する。

## 採用理由

- OS標準インストーラの更新判定と同一bundle identifierを再利用できる。
- 全OS向けの特権ブートストラップを新設せず、攻撃面を増やさない。
- モデル選択をアプリ内に置くため、インストーラ更新とモデル更新を分離できる。
- 推奨ロジックを純粋関数として単体テストできる。

## メリット

- READMEの単一導線から端末に合う候補へ到達できる。
- アプリ更新時もワークスペースと既存モデルを独立して保持できる。
- 高性能端末では文字起こし精度を優先できる。
- モデル破損や配布物の差し替えをchecksumで拒否できる。

## デメリット

- 高精度モデルは約574MBあり、初回取得と推論負荷が増える。
- ブラウザだけではMacのCPU種別を常に確定できない。
- CPU種別とメモリを使う初期ヒューリスティックで、実測速度や同時負荷を含まない。
- GitHub Pagesと公開Release APIが利用できない場合はRelease一覧へのfallbackが必要になる。

## 将来的な見直し条件

- 推奨対象端末でリアルタイム処理が安定しない実測結果が得られたとき。
- GPU backendと短時間benchmarkを安全に利用できるようになったとき。
- Tauri Updaterの署名付き自動更新を導入するとき。
- 公式モデルの配布先、サイズ、checksumが変更されたとき。
