# ADR 0005: 公開識別子を非個人化しprivacy gateを設ける

## 背景

公開前監査で、アプリ識別子、パッケージ著者、Schema URI、文書リンクに個人由来の識別情報が含まれていた。デモデータにも実在人物と誤認し得る氏名・メール形式があった。

## 課題

- 公開成果物とソースツリーへ不要な個人情報を含めない
- アプリ識別子をリリース後に安易に変更しない
- 将来の差分で絶対パス、メール、秘密情報が再混入するのを防ぐ
- デモデータが実データと誤認・誤送信されないようにする

## 選択肢

1. 現状を維持し、公開前に目視確認する
2. 個人情報だけ手動で削除し、自動検査は追加しない
3. 非個人識別子へ変更し、役割ベースfixtureとprivacy auditをCIへ追加する

## 採用した案

選択肢3を採用する。bundle identifierを`app.contextcue.desktop`へ固定し、著者表記をcontributorsへ変更する。デモ人物は役割ラベル、メールは予約済み`.invalid`ドメインを使用する。追跡候補ファイルはNode標準ライブラリによるprivacy auditで検査する。

## 採用理由

公開前であればアプリデータ領域の識別子変更コストを抑えられる。追加依存なしの監査をCIへ組み込むことで、ローカル環境固有のパスや代表的な秘密情報の再混入を早期に止められる。

## メリット

- 公開成果物から不要な個人identityを除外できる
- デモ情報を実在連絡先へ誤送信するリスクを下げられる
- CIで代表的な個人情報・秘密情報形式を継続検査できる
- bundle identifierを公開前に安定化できる

## デメリット

- 以前の開発用bundle identifierで保存したworkspaceは自動移行されない
- 自然文中の未知の氏名や画像メタデータは自動監査だけでは保証できない
- Git履歴のauthor metadataとremote identityは別途監査・移行が必要

## 将来的な見直し条件

正式な法人・組織ドメインを取得し、OS署名identityと整合させる必要が生じた場合に見直す。公開後に変更する場合は、アプリデータ移行、署名、Updater互換性を含む別ADRを必須とする。
